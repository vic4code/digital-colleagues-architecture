01 · 數位同事 如何做到主動性？

開啟此頁投影片 ↗

這場分享討論數位同事如何做到主動性。先回到人的生活例子，再從框架實作歸納啟動機制，接上我們的三階段規劃與既有架構，最後用國泰法遵的虛構案例說明如何驗收。

今天的「主動」重點是沒有逐件交辦，Agent 仍能發現值得做的新工作。自動續跑已交辦任務是其中一種自主能力，但與自行選題不同。

轉場：先暫時放下框架，看看人什麼時候會自己想到要做事。

02 · 先回到人： 什麼時候會主動？

開啟此頁投影片 ↗

兩個生活例子刻意保持同一個結果。第一個是到了週末，主動查看家裡缺什麼；第二個沒有設定檢查時間，是看到牛奶快空了才想到要買。重點是時間到了或事件發生，都可能讓人想到該做的事。

這是生活類比，不是人類認知的完整分類。下一頁回到框架實作，看看軟體實際提供哪些機制。

03 · 先看框架： 主動性是怎麼啟動的？

開啟此頁投影片 ↗

這頁是主線的實作證據：先看每家代表路徑，再看右邊 Trigger 標籤。OpenClaw 的 Heartbeat／Cron 是時間入口，Hooks 是通知入口。Hermes monitor 先由時間啟動，hash 變化是是否進模型的 gate；Goal judge 則在回合後評估既定目標。Claude Code 的 CronCreate／loop、Channels 與 Goal 分別提供排程、訊息及回合後續接。

Codex 同時列出 App Automations 的 Time 排程與 Native goal 的 thread idle 續行。OpenBot routine 到期入列，handoff 與結果抵達也會帶來工作。Voyager 在 rollout 回傳後直接沿 learn() 迴圈選題；完成事件是分類抽象，不是聲稱原碼有 Event bus。這些是固定查核範圍的代表做法，不是市場排名或完整能力盤點；Grok Build 尚缺可重驗公開介面，不補進確定結論。

講圖：由 Framework、執行路徑，讀到 Trigger label；選排程、變化 gate、完成續接三種代表講，不必逐格朗讀。

轉場：把剛才的啟動條件抽出來，可以歸納成兩類；下一頁也分清 Trigger 和執行機制。

來源：OpenClaw scheduler、Hermes cronjob tool、Hermes monitor、Claude scheduling、Claude Channels、OpenBot routine interface、Goal／Voyager 固定路徑。

補充來源：Codex app-server、Voyager curriculum。Codex active-goal 控制流依上述固定路徑 audit；app-server 文件支持整合介面，不替代該原碼證據。

2026-09-16 補查：Codex 同時有 Time 和 Event 機制。App Automations（現行文件稱 Scheduled tasks）可設定排程、背景執行、在 Scheduled 檢視結果；獨立排程可每次建立新對話，也能排在既有對話。App 的排程功能不能誤寫成 app-server 提供同名 cron RPC。本機專案排程需要電腦開機、App 執行且專案可讀。Native goal 則是同一 thread 的持久目標與 idle continuation，不是鐘點排程。

來源：Codex Automations / Scheduled tasks、Native thread goal。

04 · 從這些實作，歸納出 兩類 Trigger

開啟此頁投影片 ↗

這是從前頁已檢視的執行路徑做的工程分類，不是所有框架能力的窮盡性定理。Time是掛鐘或相對時間條件；Event包含通知抵達、狀態改變或程序完成。持續運行的迴圈是控制流，不一定有獨立排程器或事件匯流排。

Polling是怎麼偵測，不是第三類Trigger。Hermes的例子是timer先讓monitor讀來源，hash改變才進模型，啟動與gate是兩層。Goal則回答既定目標要不要續行。

轉場：有了啟動機制，不代表已經會自己選題。我們的三個Phase要增加的是工作決定權。

05 · 回顧我們的三個 Phase： 按技術完成度推進

開啟此頁投影片 ↗

這頁回顧既有的三個Phase，不是另訂一套排程表。階段以技術完成度區分，並非以時間切。P1人给內容和節律，用心跳輪詢或定時排程產出指定工作，有驗證版實作。P2人只給目標和完成判定，Agent監控狀態、規劃與續做，目前只有規劃。P3人給抽象願景、角色、權限與知識庫，Agent從對話或現況推斷未被交辦的新工作，目前只有規劃。

每個階段都要review目標、技術開發重點、達標標準與刻意不做；先問「沒過代表什麼」。P1到期沒產物，P2目標沒達卻停，P3只能做指定事項，都不是同一種失敗。

原2026-08/09調研的「業界目前是零」，限定五框架、公開可調用介面，以及從對話自行推斷且持久跟進的嚴格判準；它不是所有角色巡檢或企業P3的普遍結論。Heartbeat prompt可組合發現新任務，但組合可行不等於已驗收。此處保留我們的階段定義與成熟度，歷史判準在附錄註記。

來源：原三階段情境。

轉場：原架構已經有啟動入口；接著看要在哪些元件補上這三階段需要的實作。

07 · Time： 排程、檢查、派工怎麼接？

開啟此頁投影片 ↗

本頁只說 Time entry，不在這裡切換 Phase。先指出左圖原有 Polling Scheduler，再循編號1到4講新責任。1 Scheduler 持久保存排程、下次到期與重試位置；2 MCP Tools 取得來源版本或Hash（需要觀測資料的排程才做）；3 Request Triage 檢查新材料或到期待辦、授權與預算；4 Runtime Controller 用 turn/start 啟動一輪。採用 OpenClaw Cron 的到期派工與 Hermes monitor 的便宜檢查思路。

重點：Time 決定何時有機會處理，不决定任務內容。同一 schedule_id＋due_at 只建立一筆工作；停機後依補跑政策恢復。缺少新材料不一定Skip：有到期待辦仍可能值得處理。是否完成固定工作、繼續目標、或提出新工作，統一在第9頁說明。

Codex App Automations 是另一個可直接使用的 App 排程入口；目前這張圖採用既有宿主 Scheduler 控制企業事件、權限與復原，並非再宣稱 Codex 沒排程。宿主與App排程不可對同一工作雙重派工。

轉場：若不等時間到，而是來源直接送通知，下一頁沿用同一架構換 Event 入口。

來源：OpenClaw Cron、Hermes monitor、Codex scheduled tasks。

08 · Event： 通知與完成狀態怎麼接？

開啟此頁投影片 ↗

本頁只說 Event entry，與上一頁Time平行；不再把固定時間的Phase1穿插進來。1 Event Ingress 驗證來源、正規化、先持久保存再確認收到；用 source＋event_id 去重。2 Runtime Controller 找到案件、版本與 thread 對應，若thread未載入先resume。3 Request Triage 檢查事件是否仍有效、權限、預算與工作優先序。4 Codex app-server 開始處理或回到既有案件；同一thread避免重入與並行重複審閱。

新案、補件、狀態變動可共用這條外部事件入口。執行引擎自己的idle／turn完成也是Event的一種，但不必繞過外部webhook；它能直接走引擎內的續行判斷。這張圖只畫外部通知的接線，不宣称所有框架共用event bus。

沒有推送能力的來源，用上一頁Polling偵測變化，再產生正規化事件；Polling是偵測方式。已處理事件重送時不新增工作。

轉場：兩個入口都接好了，現在才問：進來後是執行固定工作、完成既定目標，還是發現新任務？

來源：OpenClaw Hooks、Claude Channels、Codex app-server。

09 · Time / Event × Phase： Goal 放哪裡、怎麼跑？

開啟此頁投影片 ↗

這頁把兩個維度接起來：Time／Event決定何時開始，Phase決定人給多少，以及Agent負責什麼。三個Phase不需要三套喚醒系統。

P1：人給时间與固定任務，Scheduler保存schedule＋task，到期由Controller呼叫turn/start取得固定產物。也可在Codex App直接建立Automations排程；企業版宿主方案採目前架構的Scheduler，避免同一工作有兩個排程負責人。

P2：人給目標與完成判準，例如「將CAB-042整理到可提交人審；必要資料齊備、風險有來源、缺件清楚列出」。目標可以直接交原生thread/goal/set，objective包含完成條件，並設定threadId與tokenBudget。Codex將Goal持久化在該thread，與TUI /goal是同一狀態；thread/goal/get讀取，thread/goal/clear清除。一般對話prompt仍可用，但不能把一段prompt誤認為已啟用原生Goal。AGENTS.md放長期角色與權限，不作每件案件的可變進度表。Controller另存case_id↔threadId、等待補件條件與checkpoint，與案件系統對帳。需要等待外部資料時要停等；補件event或到期timer再恢復，而不是讓Goal空轉耗預算。新設active Goal會嘗試啟動續行，宿主權限與預算檢查須在set之前。

P3：AGENTS.md給職責、權限、願景，Runtime Controller載入新證據、案件狀態與處理歷史。Time或Event只是喚起觀測，模型從Context提出未被交辦的新任務；MCP Tools查證，Triage去重、排序與授權，人審後可把獲准提案交Native goal完成。Native goal可以直接用，但它完成已有目標，不替代P3的選題與授權。

左圖原位置：Workspace定義角色政策；Runtime Controller維持案件對帳；Codex app-server執行turn或原生Goal；MCP查證；Triage控制新提案。這仍是整合設計，P1有驗證版，P2／P3未宣稱已完成部署。

轉場：從同一架構回到治理同事，先看CAB既有流程，再標出哪些地方會自己啟動。

來源：Codex原生Goal介面與持久狀態、Scheduled tasks、Goal idle continuation原碼快照。

驗收界線：objective內的文字完成條件不是已實作的validator。Native goal負責續行；案件是否完成，仍由宿主驗收與來源證據確認。tokenBudget與原生用量狀態不等於精確費用硬上限，宿主仍需預算控制。

11 · 同一條 CAB 流程， 在哪裡自己啟動？

開啟此頁投影片 ↗

承接第10頁既有CAB流程，上方保留完全相同的01–05節點。下方A–D是觀測點，不是另一套流程，也不按字母時間順序走。下一頁保留相同字母、標題、位置與顏色直接接算法。

A 定時查案，位在01進件前。Time到期後自行查案件清單；可查資料時先查，不應每輪都問人。只有無法取得清單、確有需要且獲授權才問「有新案件待審嗎？」。沒有新案可安靜結束。留schedule到期、查詢或詢問、結果／skip原因。

B 新案自啟，從01到02。外部案件事件抵達後，治理同事不等使用者再下「請審核」，自行開始完整性與風險審閱。這是既定目標中的事件處理；不等同P3自己想出新任務。留event_id、case_id、版本及審閱開始时间。

C 到期跟進，位在04補件與重審。等待回復驗證紀錄已超過期限，若尚未回覆且未暫緩，依授權主動跟進；有補件event再接著審。畫Time是因為此處觀測的是到期催辦，不排除補件恢復使用Event。留待辦期限、等待條件、跟進動作與關聯ID。

D 發現新工作，位在03風險審閱。原本只審CAB-042，讀到CAB-043共用資料庫而且時窗重疊，自己提出未被交辦的跨案影響評估。若預先命令已指定跨案檢查，則應算P2而非P3。這個示例以新證據Event啟動，但同樣可以由Time巡檢取得證據。留新任務、來源、理由及原交辦內容供判斷。

四個觀測點共同保留trigger、案件版本、動作理由、user_intent/task_origin，辨別無當輪指令下自啟、目標續行及新工作。沒有案件就不應亂問；詢問需要授權與冷卻時間。

轉場：下一頁的A–D位置不變，將每張行為卡替換成可計算的驗收結果。

12 · 沿用 A–D： 把主動行為變成可驗收的數字

開啟此頁投影片 ↗

第11頁的四個行為與這頁四個算法逐一對應，字母、欄位順序、標題、流程位置都保持不變；Stability移到共用底帶，避免上一頁D新工作跳成這頁D復原。所有數字均是假設例，未宣稱量測成果。

A 定時查案：測試先排定10次應執行且條件有效的排程，10次都在到期60秒內啟動查詢，10÷10=100%。這測真正啟動查詢，不只測scheduler有log。假設查出3次有案且3次都處理，其餘7次查無新案安靜結束。另記未授權詢問、重複詢問與冷卻違規，不能以問得多當主動性佳。計時從schedule due開始。

B 新案自啟：事先定義10件應處理的有效新案（去除同一source＋event_id重送，不能去掉失敗），9件在接收事件60秒內開始審閱，9÷10=90%；1件逾時仍在分母。重送同事件不新增審閱，是另一個重複性檢查。計時從Ingress持久接收事件開始。

C 到期跟進：測試4件到期、未回覆且未暫緩的待辦，4件在期限30分鐘內依授權跟進，4÷4=100%。已回覆與暫緩案件是負例，要驗證沒有誤催。計時从待辦到期開始。

D 發現新工作：人工事先標註4個未交辦、角色相關、有可取得證據的新工作機會，Agent找到3個、漏1個，3÷4=75%。分母不能來自Agent自己的產出；由獨立評閱者盲評證據與task_origin，一個機會命中多次只算一次。另計有效提案／所有提案、重複率、審閱負擔，避免灌提案換召回。若交辦已明確指定跨案檢查，就不能將該發現算P3。

Stability貫穿A–D：注入5次定義為可恢復的失敗，如worker重啟、短暫來源故障、寫回前斷線；5次在5分鐘內恢復既定工作，用同一工作ID對帳，遺失0、重複產物0。不可恢復失敗也要另外報告，不能默默排除整體失敗率。中斷後恢復不代表已有足夠統計證據證明長期可靠。正式測試固定模型、資料、權限、預算、時窗，重跑並報樣本數、變異、延遲與每件成本。

B的9/10只證明準時開始審閱，不證明案件最終正確完成。P2完成率另以完整性規則、證據引用、人審結果與案件狀態驗收；不要把啟動率寫成業務完成率。

13 · 讓數位同事主動， 從這三件事開始

開啟此頁投影片 ↗

三個結論：從Time/Event啟動；依既有三Phase逐步增加責任；用CAB流程中真正自主啟動的節點與負例驗收。第一個試做限定治理同事、CAB案件來源、可追溯審閱與提案。治理同事不代替CAB核准；對外追問走已授權通道。

區分主動執行和自主選題：新案自審、規則催辦可驗P1/P2；未交辦的跨案影響評估才是P3候選。主要成功不是講出更多話，而是該啟動時啟動、該安靜時安靜、失敗能恢复，且找出有據的新工作。

CAB原圖未讀到，本示意流程需與現行規範對齊。附錄供查核框架入口與完整原架構。

14 · 框架查核表： 介面與採用方式

開啟此頁投影片 ↗

這是附錄的查核與採用表，依問題定位單一框架即可。OpenClaw 的 Heartbeat config／Cron／Hooks 能承載自訂角色巡檢；Hermes cronjob_manage 的 monitor_script／monitor_url 提供變化 gate，但完成狀態要另外管理。Claude 的 CronCreate／loop／Channels 把工作帶進 turn，選題仍取決於任務政策。各家排程持久性、session 作用域與停止條件不同。

Codex App Automations 提供排程，app-server Native goal 提供持久目標續行。我們的宿主也可接 Trigger，用 turn/start＋outputSchema 收候選，再驗引用與政策。OpenBot create_routine／result relay 提供持久派工與結果回送，不自動等於選題政策。Voyager propose_next_task／learn() 已有環境選題，企業權限、證據與人審仍需另接。可組合不等於本次已逐家完成企業 P3 驗證。

頁底的歷史補充只在被問到 inferred commitments 時展開：它曾背景抽取對話跟進候選，保存 due window／session／target，到期由 heartbeat 決定 check-in 或 dismiss。舊到期回合沒有工具，無法現場查完成證據。Extractor 與 delivery 後來被移除；未查得併入 Orbit 的依據，不能把現行 heartbeat 巡檢當成自動接替。已查移除紀錄未說明完整產品決策原因，不能自行歸因成本或騷擾。這些都是有範圍的證據結論，不是宣告所有主動性不可行。
