# 同事互動感：不只會回話，還要讓合作接得下去

[研究入口](README.md) · [互動情境版](show-me-colleague-interaction.html) · [主動工作研究](proactive-work.md)。更新：2026-09-11。

## 先給老闆看的概念

**主動工作**問「不用人催，會不會回來看、繼續做」；**同事互動感**問「跟它說話、改方向、一起做事時，是否省心、接得上」。即使每次都由人開口，Agent 也可以有好的同事互動感；定時發很多訊息則不保證有。

互動的最小循環是：**理解現在誰在等什麼 → 選擇適當的回應與動作 → 保留共同脈絡，讓下一步接得上。** 這是本研究的設計整理，不是 framework 的原生通用 pipeline。

## 一件工作怎麼聊完、做完

| 情境 | 希望它怎麼互動 | 底層需要什麼 |
|---|---|---|
| 「幫我整理下午開會資料」 | 簡短說明接手與第一步，開始做 | 收件確認、工作 owner、可見回覆 |
| 工作途中：「改用九月資料」 | 接住修正，調整同一件工作 | steering／queue、工作 revision、過時結果撤換 |
| 「做到哪裡？」 | 說明具體已完成、還缺什麼 | 真實進度、阻塞、下一步，不是只有 typing |
| 群組裡 Alice 已經回答 | 沒有新增價值就不搶著重複 | 發言對象、群組 context、reply／reaction／silence 選擇 |
| 要 Alex 幫忙補一份資料 | 說清成果、需要時間與背景；交接後記住等待 | 收件人身分、權限、handoff、awaiting_reply |
| 工作完成 | 給成果與證據，讓接收者能直接使用 | result delivery、連結／附件、送達狀態 |
| 感謝、問候、簡短閒聊 | 自然且適量地回應，不把每句話變成任務 | reply／reaction 選擇、場合與風格 |
| 下次又遇到相同工作 | 接回已確認的偏好與修正 | scoped memory、routine、來源與覆寫規則 |

## 哪些有現成證據，哪些是我們的提案？

### Grok Bot：把人正在等的回合，與背景回合分開

官方產品頁描述連續對話、workflow 學習和 Bot 協作；這是產品方向，沒有提供互動品質測量。[官方介紹](https://x.ai/news/introducing-grok-bot)

非官方 0.18 重建 `system-prompt.ts` L82–100 可見：使用者開啟回合要先回應；背景 wake 可先工作；對外訊息走 SendMessage；有些簡短社交回應可用 reaction；使用者正在等的成果不能只留在模型內文。這同時需要 prompt 與實際訊息工具，不是只靠寫「你是好同事」。[固定來源](https://github.com/b-nnett/grok-bot-0.18-reconstructed/blob/a9f633e09d49a85829b8236331b9e21f7e612634/source/host/runner/system-prompt.ts#L82)

這份重建不能用來證明官方二進位完全一致；prompt 是預期行為，也不能保證每次遵守。完整版本限制見 [Grok 查核](source-notes/grok-reconstructed.md)。

### OpenClaw：發言時機、上下文與改方向有具體機制

WhatsApp 群組文件區分 mention／always activation；always 可以喚醒後仍選 `NO_REPLY`，pending group messages 可作下一輪 context，群組與私訊分開 session。**「收到資料」「喚醒模型」「公開發話」不是同一件事。** 此處只引用 WhatsApp 行為，不把所有 channel 的細節視作相同。[固定文件](https://github.com/openclaw/openclaw/blob/d36ca99e50d161d117e747ed18482ae715c53b8b/docs/channels/group-messages.md)

Queue 文件分 steer、followup、collect、interrupt：分別對應把新話接入目前工作、留下一輪、合併連續訊息、或中止後重開。這直接影響「你補一句，它是否還繼續做舊版本」。正在執行的外部動作未必能撤回，不能把 steering 描述成時間倒流。[目前官方 queue](https://docs.openclaw.ai/concepts/queue)

Typing indicators 讓使用者知道回合在運作；它不代表有進展或保證完成。UI 若顯示「處理中」，應對應真實 runtime 狀態。[固定文件](https://github.com/openclaw/openclaw/blob/d36ca99e50d161d117e747ed18482ae715c53b8b/docs/concepts/typing-indicators.md)

### 共同記憶與責任：兩條主線共用

Memory 幫它記得背景；work state 記它還欠什麼；delivery state 記它說了與送了什麼。共享群組只使用該群組可見的記憶與已授權資料，不能因為「像熟同事」就跨私訊引用資訊。記憶需能修正，期限或收件人變更後以最新有效版本為準。[既有共同狀態設計](source-notes/colleague-experience.md)

## 本專案要補的互動契約

這是 proposed design，不宣稱各框架已自動實現全部行為。

1. **接手有內容。** 短任務直接回答；長任務簡短說要做什麼。不要對每個背景 timer 都發「收到」。
2. **更新有變化。** 回報已完成、發現、阻塞或需要的決策；避免固定秒數刷一句空洞進度。
3. **修正能生效。** 連續訊息可合併；使用者改方向時提升工作 revision，未送的舊草稿不再送。已執行的動作據實說明。
4. **群組知道何時說話。** 被問到、被交辦或有實質補充才回覆；其他人已接手時不重複搶 owner。既有規則可控制是否允許主動介入。
5. **交接保留責任。** 找對人、交代背景與期待成果；發出訊息後留下 owner 與等待狀態，不把「送出」當成「完成」。
6. **日常交流自然，資訊準確。** 感謝與閒聊可以簡短回應，不必硬接成工作提案。 簡短、符合對象，引用具體工作；不知道就說不知道。不要用假裝忙碌、情緒或人際關係製造存在感。
7. **回來時接得上。** 保存確認過的偏好、對話與工作摘要，能看出來源；使用者修正後更新，不永久沿用錯誤推論。

## 不只是催進度：互動研究的獨立驗收

| 測試 | 觀察什麼 | 不能用什麼充數 |
|---|---|---|
| 同一需求分三則訊息補充 | 有無合併理解，是否少問已回答的問題 | 發三次「收到」 |
| 工作中改時間／資料版本 | 最終成果採最新版本，舊動作如實交代 | 聊天上答應、實際仍做舊版 |
| 兩人同時交辦／一人接手 | owner、優先與交接清楚，不搶答／重做 | 單純增加併發 |
| 群組中有人先給出完整答案 | 能安靜或僅補充必要資訊 | 每則都插話 |
| 長任務需要使用者判斷 | 帶已查到的資訊與具體選項提問 | 整段工作丟回給使用者 |
| 使用者只問進度 | 回答真實狀態，原工作繼續 | 另開一件「查進度」而遺失原任務 |
| 換一天、換 thread 再提起 | 在允許的 scope 內找回共同背景 | 把別人的私訊拿來補 context |
| 使用者糾正偏好 | 後續真的調整，且能再改回來 | 自稱越來越懂你 |

衡量：需要使用者重講的次數、改方向成功率、重複插話率、交接遺失率、成果可用率與使用者主觀協作負擔。先用合成情境和人工評分建 baseline；不虛構「同事感分數」，不把產品行銷文當成驗收結果。
