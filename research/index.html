主動性，在於自己產生「值得做的事」。

從人的「想到」，拆到 Agent 的實作

人看到新報表，聯想到下午會議與自己在意的會議品質，於是產生「先核對簡報」的工作。也可能只是時間快到了，便想起要檢查。這是理解主動性的情境類比，不是人類認知的完整模型。

對 Agent：Time／Event 決定何時有機會觀察；角色、記憶與現況提供聯想材料；推論產生候選工作，再依證據與權限選擇查證、提案或不動作。排程本身不會替它想到工作。

還有第三種嗎？執行中的 loop 怎麼算？

本研究以 Time／Event 分類觸發來源。狀態跨過門檻、程序完成、串流資料抵達，都屬於 Event；「上一輪完成」也是內部 Event。while 是實作控制流，不是第三種觸發來源，也不需要 event bus。記憶、環境與好奇心則是選題的輸入或策略。

往下拆：喚醒、產生想法、選擇與執行，各負責什麼？
Time／Event：何時開始觀察？

排程、來源事件或內部完成事件提供執行機會。只有 timer 與 queue，還不能證明系統會發現新的工作。

Generate／Select：如何想到與選出工作？

把可存取的現況、職責與記憶放入 context，讓模型推導「有什麼值得處理」，以證據與政策篩選。可以直接提出一件事，不必實作獨立候選池或數值排名器。

查看選題研究與框架邊界 ↗
Execute／Continue：想到之後如何做完？

這是後段能力：工具、授權、任務狀態與 loop 讓選定的工作完成。接續既定目標，是與「發現一件值得做的事」不同的能力。

人的部分是行為類比。Agent 在已設定職責與可觀察範圍內推導工作；此圖是本專案設計抽象。

跨框架歸納：Time／Event 觸發，選題策略決定做什麼

觸發來源分為 Time／Event。狀態跨過門檻、程序完成、串流資料抵達，都屬於 Event；可由 polling 偵測，也可直接推送，不代表一定有 event bus。選什麼工作則由 curriculum、目標或就緒任務政策決定；續行迴圈管理執行，學習／整理更新下輪材料。

三個容易看錯的例子：Hermes 遠端 cron 用 HTTP 送達，語意仍是定時；Kanban 用 polling 發現 ready，任務資格由依賴狀態決定；Voyager 在執行迴圈內根據環境選題，沒有固定選題時鐘。

Polling：定期讀來源，再比對變化；不必每次呼叫模型。

Polling、Heartbeat、Cron 不是三種觸發器？

Polling 是取資料的方法；Cron 是排時刻的方法；Agent Heartbeat 是週期喚起「看一看」的回合。可以用 cron 排 heartbeat，再在回合內 polling。它們可以疊在一起。

Event 一定比 polling 好？

Push 可降低延遲與無效查詢，但要處理重送、亂序、漏接與訂閱續期。沒有可靠 push 的來源用有界 polling；事件接入也可保留補查。Claude Code 的 Telegram channel 底下也會 polling，所以「模型收到 event」不代表來源端完全沒輪詢。

Voyager 看 environment，不也是時間到讀 context？

查到的 learn() 是 while → 選題 → rollout → 更新紀錄 → 下一輪；不是每隔 N 分鐘選題。wait_ticks 讓環境動作穩定，API 重試也可能 sleep；它們不是選題 cron。

直接看 learn() ↗
狀態門檻、完成、串流，不也都是 Event？

對，都是 Event。這裡分三層：觸發來源是 Time／Event；偵測與傳遞可用 polling、callback 或 queue；選題靠職責、脈絡與策略。持續迴圈是控制流，不另列成第三種觸發來源。

每次 heartbeat 都花模型費嗎？

不一定。先用確定性准入與來源差異擋掉無效回合；Hermes monitor 在 hash 未變時跳過模型。「零模型」仍有 I/O、CPU 與服務成本。

為什麼舊研究打勾，新表卻寫「未證」？

準則與版本不同。此表要求可用介面，且把目標續跑與自行推斷跟進分開。以來源版本說話；某段 durable goal 資料結構存在，不代表該部署已接上自動續跑。

新報表到了，
數位同事怎麼決定要不要做事？

沿用開場的下午會議情境。下列是預計接進原架構的運作方式。

  1. ↗收到線索報表 v3 更新了Event Ingress／Scheduler
    元件做什麼？

    來源推送事件，或排程檢查發現更新。保留來源、時間與事件識別，讓後面知道為什麼醒來。對應 W0、W1a。

  2. ◇先判斷要不要跑有新資料，現在可處理嗎？Runtime Controller／Triage
    元件做什麼？

    用程式檢查啟用、暫停、間隔、忙碌與新素材；不需要模型。若沒有新資料，就留下原因並結束這一輪。對應 W1b。

  3. ≋補齊工作脈絡下午有會議，簡報仍是 v2Controller 載入角色／記憶＋MCP
    元件做什麼？

    確認會議支援角色與權限；查看是否已處理、是否在等人；只取這次相關的報表與簡報。角色投影與任務對帳仍待補。對應 W2–W4。

  4. ✦想到值得做的事先核對，再提出修訂建議Codex app-server＋MCP Tools
    元件做什麼？

    Phase 3 提案：模型依職責與資料推導「值得比對」，在授權範圍查證後產出建議。Phase 1 則只做人指定的固定清單；不能把同一個流程骨架當成已有自主選題。對應 W5。

  5. ✓提案並記住結果等你決定，下次不重提Triage／Interaction surface＋State
    元件做什麼？

    程式檢查提案與重複紀錄，合格才進私有收件匣；留下稽核與處理進度。沒有合格提案也記原因。記憶與狀態存放、寫回接線需按 Phase 補齊。對應 W6、W7。

這次監看沒有新資料？在第二步結束 → 記錄原因 → 等下次喚醒這是報表監看情境；待辦到期或等待條件改變，也可能需要處理。

05 / CATHAY SCENARIOS & EVIDENCE

回到國泰，
怎麼用、怎麼證明？

指標的分母怎麼算？
指標定義避免誤讀
喚醒覆蓋率有結果的到期 occurrence／應到期 occurrence分 timer、event、human、inbox-open；模型呼叫數不是主動次數
有用提案率人工判定有用／已評閱提案未讀另列；只看採納無法知道漏判
機會召回率有提出的標註機會／全部標註機會需離線標註集或定期人工抽查，不能從線上提案自算
無證據／重複提案率不合格提案／所有生成提案保留 W6 被擋的提案，才有分母
注意力與成本標題已讀、內容開啟、接受／退回／延後；每次有效提案成本不把開過等同有用；含生成後被擋成本
可靠性來源延遲、W 階段耗時、恢復時間、預算耗盡、cursor lag零模型不等於零資源成本；trace 是理由與證據，不存隱藏思考鏈
