OpenBot pinned source review

Reviewed 2026-09-08. Repository CopilotKit/OpenBot, commit 7b94a0b802732e6491634160cf9ed3fcfb813424 (2026-09-06T21:06:23Z). Local root /tmp/proactive-agent-research-20260908/source/openbot/OpenBot-7b94a0b802732e6491634160cf9ed3fcfb813424. This is source/test inspection, NOT execution of the tests and NOT live deployment validation. No dependencies installed. OpenBot identity remains a provisional interpretation of the user's ambiguous “open bot”.

All relative file+line references below resolve at https://github.com/CopilotKit/OpenBot/blob/7b94a0b802732e6491634160cf9ed3fcfb813424/ (append #L).

Main conclusion

The source implements user-delegated scheduled work plus dynamic task handoff, with durable identity, permissions, history and execution controls. It does not furnish evidence of an endogenous curiosity/novelty scoring process, a self-generated curriculum, or a standing pool of candidate goals selected during idle time. The existing agent can make tool/next-step decisions inside a prompted run, and a routine instruction may authorize exploration or schedule mutation; those are extension points, not a built-in intrinsic-motivation subsystem.

Complete trigger-to-execution chain

  1. Conversation becomes a tool call. server/src/plugins/builtin-routines.ts:74-124 declares create_routine with instruction, five-field cron, optional timezone and channel. The model translates the user's sentence; this is prompt-mediated interpretation. Its tool description explicitly separates the work of ONE firing from the schedule. Runtime callTool at :356-398 takes owner from connection.actorId and bot from connection.botId, ignores spoofed owner/bot arguments, then calls the store. Actual tool availability and invocation are permission mediated: server/src/plugins/tools.ts:157-183 loads granted tools and calls store.callTool; server/src/plugins/store.ts:2785-2812 rechecks decide("mcp", input.ref, input.botId) and refuses before invocation. No model permission assertion substitutes for these checks.

  2. Persist intent and next occurrence. server/src/routines/store.ts:512-550 validates instruction, resolves a channel in which the owner belongs, defaults timezone UTC, computes nextRunAt, then inserts under withEnabledCapLock (:424-433). This lock uses Postgres advisory transaction locking around the per-owner 20-enabled-routine count so racing creates cannot bypass the cap. The schema server/src/db/schema/coworker.ts:93-125 stores ownerUserId, agentId, channelId, instruction, cron, timezone, enabled, nextRunAt and lastRunAt. It is a schedule ledger, not a goal generator. server/src/routines/schedule.ts:100-173 validates sub-floor intervals and obtains cron-parser next occurrences; minimum interval is 15 minutes. Cron/timezone/enabling updates recompute from current time (store.ts:450-505).

  3. The waking process is deterministic polling. worker/src/index.ts:88-105 uses TICK_MS=30_000; runOneTick at :110-129 runs offerDueRoutines then dispatchClaimedRoutines; the main loop at :163 sleeps after a tick. It invokes no idle-reflection model prompt. Kubernetes uses the same sweep via server/scripts/fire-routines.ts from an external CronJob.

  4. Offer due work and move the schedule. server/src/routines/store.ts:663-688 selects enabled rows with nextRunAt <= now() using database clock. server/src/routines/sweep.ts:135-196 offers key <routine-id>:<UTC-due-minute> to the shared queue before advancing the stamp. store.ts:690-735 compare-and-sets the old stamp. Stale occurrences outside the 10-minute grace are skipped and the next occurrence is calculated from now. This is a temporal relevance heuristic, not learned value-of-information selection. The next occurrence is scheduled BEFORE the current model run finishes; completion does not generate a successor goal.

  5. Claim and dispatch. server/src/work/queue.ts:268-330 uses a transaction, FOR UPDATE SKIP LOCKED, database-clock lease eligibility and attempts < cap, then records lease owner and increments attempts. sweep.ts:260-443 claims, renews, rereads whether routine is enabled/present, checks age, creates a run row, calls dispatch, and finishes the queue row after HTTP acceptance. worker/src/index.ts:66-84 posts the run id to the internal API with a bearer secret and bounded HTTP wait. server/src/app.ts:812-878 validates the secret/body, invokes detached routineRunner.run(...), and returns 202. Queue delivery acceptance is NOT model success.

  6. Resolve current owner and build the actual agent. server/src/routines/runner.ts:72-135 reloads run context and owner-accessible channel; missing channel yields skipped without model spend. server/src/index.ts:661-703 calls actorFor(ownerUserId) freshly, loads actor-visible agents, actor tools, signed run identity, current standing instructions, and selects the routine's agent. Deleted/invisible agent throws. server/src/copilot.ts:271-300 composes built-in prompt from agent systemPrompt, user standing instructions, provenance and current capabilities. Thus persisted identity does not freeze obsolete rights.

  7. Frame a firing, seed history, run. server/src/routines/run-turn.ts:246-253 wraps instruction: it is firing now; perform the work this turn; do not create/list/change routine unless instruction asks. This is a PROMPT restriction, not a tool removed from the agent. :281-399 creates/gets thread, retrieves/sanitizes history, adds the framed user message, builds agent, sets its messages/thread, passes no frontend tools, and acquires a thread lock. :458-482 actually calls runner.run({threadId, agent, input, persistedInputMessages}); RUN_ERROR emitted as a normal observable event is explicitly converted to failure.

  8. What heartbeat really does. run-turn.ts:86 sets 15-second heartbeat; :437-452 only calls ɵrenewThreadLock. It does NOT read workspace, choose a goal, reflect, or invoke an LLM. Failure clears heartbeat and calls agent.abortRun() plus runner.stop() (:425-435). The 5-minute deadline and 5-second abort grace are at :76-79 and :485-499; finally releases lock and timers (:502-520). Other heartbeat variables in agents/handoff-runner.ts:263 and handoff-delivery.ts:325 similarly renew ownership/locks.

  9. Completion and unattended limits. run-turn.ts:522-570 rejects heartbeat loss, timeout, pending human interrupts, and an empty reply. A routine that asks for human input is marked failed, not retained here as a pause/resume workflow. runner.ts:137-178 records failed status, sends first failure notice, disables after 10 consecutive failures, or posts reply and records succeeded. store.ts:813-842 finishes only an unfinished run. Success is execution completion with reply, not a semantic proof that business work was correctly accomplished.

  10. Pause does not establish in-flight cancellation. store.ts:632-636 setEnabled delegates to update; re-enable recomputes next time. Sweep rereads enabled before dispatch and drops queued work when disabled. runContext only selects routine id, owner, bot, channel and instruction (store.ts:758-780); it has no enabled field, and runner has no enabled/cancellation check. Source therefore supports blocking future/pending firings, not a claim that the routine toggle aborts an already accepted turn. The common thread runner has independent abort/deadline controls.

Dynamic handoff: initiative inside a task

server/src/agents/handoff-tool.ts:23-44 uses structured bot/task/constraints/expecting; :74-94 offers no tool without grants or at depth/fanout disable. The model decides when delegation helps, but authority and budgets are code. handoff.ts:145-170 checks signed depth; :191-271 resolves current actor-visible target, rejects missing/self target, and rereads grants; :295-330 hashes actor/run/target/task/constraints/expecting for idempotence and atomically offers under per-run cap. Repeated content is not new work. At cap, it instructs model to answer with what it has or ask the person (:350-356).

Delivery is event-driven: server/src/index.ts:972-1009 serializes per-replica sweep, uses PostgreSQL work-offered notification plus 2-second polling backstop. It reacts to queued bot.message, not environmental novelty. :895-923 builds target as current actor, executes target on a scratch thread and relays answer to original conversation (implementation comments warn thread ownership means original asking Bot's voice, so avoid simplistic claim every target posts directly as itself in original thread). handoff-runner.ts:263-274 renews queue lease. These workers do not spontaneously populate the queue.

The example remote LangGraph loop (agent-langgraph/src/index.ts:331-385) runs answer -> deployment tools -> answer until no tool call, or ends when tool requires a surface/human. It is a model-controlled action loop within an input run, not a repeated unsupervised mind. Comment mentions recursionLimit, but invocation at :404-410 supplies only {version:"v2"} and no explicit numeric recursionLimit: do not invent an OpenBot-specific max-step value from that comment. Built-in actors instead use CopilotKit agent runtime; remote AG-UI endpoints can implement other loops.

  • server/tests/routine-schedule.test.ts:28-95: floor covers every minute, five minute, disjoint yearly/overnight adjacent pairs, accepts valid interval; :10-26 checks local 09:30 across DST.
  • server/tests/routine-sweep.integration.test.ts:276-302: two actual DB sweeps in Promise.all leave one work row and exactly one stamp advance. :427-451: month-old task creates no firing, recent one fires, stale nextRunAt catches up in one pass. :684-704: disable after offer produces no dispatch/no run row and finishes work item. These are integration test definitions, not evidence they passed today.
  • server/tests/routine-run-turn.test.ts:238-316: mocks assert thread creation before lock before run, seeded history plus firing message. :337-380 documents previous live regression: schedule-shaped instruction caused list_routines + already-configured answer without actual work; asserts framing now distinguishes execution from setup. This illustrates why scheduler + prompt is not semantic task success.
  • routine-run-turn.test.ts:621-657: forced timeout/renew failure aborts, releases lock, stops renewing. :821-862: empty output and pending human interrupt throw; tests specifically do not treat either as a completed background task.
  • server/tests/routine-runner.test.ts:214-232: tenth failure finishes failed, disables, sends final message; :235-245 no accessible channel means no turn, skipped ledger.
  • server/tests/agent-handoff.test.ts:176-187: signed depth at cap yields refusal and no queued row; :260-286 no grant/self prohibited. These reinforce bounded task delegation, not endogenous goals.

Limits and substantive absence assessment

Inspected control flow above, runtime prompt composition and shipped tenant prompts (examples/fintech/agents.yaml), all database schema inventories (server/src/db/schema/*), routine/task queue producers and consumers, plus whole repository .ts/.md/.yaml keyword pass (excluding tests) for heartbeat/proactive/curiosity/intrinsic/curriculum/webhook/exploration. Only lease/lock heartbeat matches appeared. Schema offers roles/instructions, channels/history mapping, routine schedule/run status and generic queued payload, with no explicit opportunity store, curiosity score, uncertainty frontier or exploration curriculum. Core wake paths inspected consume schedules, user turns, or existing handoff work. No inspected prompt says idle agents should invent and pursue independent goals. This bounded source audit supports “no built-in autonomous exploration mechanism evidenced in reviewed core”; it cannot rule out custom plugins, arbitrary remote AG-UI agents, tasks encoded as free text, or model behavior inside authorized tools.

Reliability qualification: sweep.ts:426-445 warns routine-fire-redelivery-possible when lease expires after dispatch; HTTP timeout can also mean accepted-but-unacknowledged (:405-416). Therefore source has idempotent offering/concurrent claim protections, not unconditional exactly-once external side effects. No production execution or test suite was run in this review.
